# MS-2 — Scoring: Design

> Design output (2026-09-06, **owner not in the loop — every §1 decision is _proposed_ and may be overridden before the plan is cut**). Instantiates master-spec §19 "MS-2 — Domain logic" as five sequenced sub-milestones, each with its own implementation plan and its own `dev→main` PR, the way the [MS-1 ingestion design](2026-07-05-ms1-ingestion-design.md) instantiated §19 "MS-1 — Core workflow". The master spec and ADRs remain the design source of truth; this document records the MS-2 *decomposition* and the scope decisions it proposes. It introduces no new architecture except where §1 says so explicitly and marks it a proposed decision — every other mechanism below is fixed by an existing ADR or spec section, cited inline.

**Goal:** every listing carries a **reproducible** 0–100 `deal_score` computed per [ADR 0011](../../adr/adr-0011-composite-deal-score.md) — the weighted geometric mean `base = Π_k max(s_k, 0.02)^{w_k}` at **price 0.50 · fitness 0.25 · seller 0.15 · availability 0.10**, gated by the three non-compensatory veto caps (**device-managed SMR for an enterprise/NAS buyer → 35**, **used/seller-refurb with no returns → 60**, **seller trust < 0.50 → 60**), with `deal_score = round(100 · min(base, cap))` — together with the DR-004 per-subscore explanation payload; thin cohorts (`n_eff < 30`) visibly shrink toward neutral and are marked **provisional**; and the documented cohort-relaxation fallback fires when a cohort is too small (master-spec §19 MS-2 acceptance, line 916).

### MS-2a — Scoring substrate

- **`ListingScore`** — hypertable on `scored_at`, composite PK `(listing_id, scored_at)`, monthly chunks (the `0003_offer_snapshot_hypertable.py` precedent). Columns: `deal_score` (0–100 int), `base_score`, the four subscores, `cohort_key`, `cohort_baseline` FK, `n_eff`, `lambda_shrinkage`, `is_provisional`, `cap_applied` (nullable int) + `cap_reason`, `risk_flags` (jsonb array), `dollars_per_tb`, `price_basis`, `inputs_json`, `explanation_json`, `explanation_text`, `algorithm_version`, `matcher_grain` (the resolution grain the score was computed at), plus `RetentionGoverned` per S2-2.
- **`CohortBaseline`** — plain table (not a hypertable: one row per cohort key per computation, ~10² cohorts at v1). Columns: `cohort_key`, `computed_at`, `observation_count`, `n_eff`, `ln_price_per_tb` distribution summary (the quantile points the percentile and the IQR margin need), `window_days = 90`, `half_life_days = 30`, `relaxation_step` (`none` / `condition` / `capacity` / `tier`), `algorithm_version`. `retention_class = merchant_fact`, indefinite (S2-2).
- **`SellerRatingObservation`** — append-only, `RetentionGoverned`; eBay-sourced rows carry `ebay_listing_observation` (IR-002).
- The §2.1 field additions, including the `market_tier` enum data migration.
- **No scoring math in this sub-milestone** — it must be mergeable and deployable on its own without changing any observable behavior.

### MS-2b — The pure scoring library

Every quantity below is ADR 0011's, reproduced exactly:

- **Weighting and decay:** `w = 2^(−age_days/30)` (30-day half-life) over a **90-day rolling window**; `n_eff = (Σw)²/Σ(w²)`.
- **Price:** `q` = the **weighted cheapness percentile** of this listing's `ln($/TB)` within its cohort; `s_price = λ·(1−q) + (1−λ)·0.5` with **`λ = min(1, n_eff/30)`**. `n_eff < 30` ⇒ `is_provisional = True`. (The ratified target is 30, not 50 — the ADR's own Decision Outcome records why: a 64-observation cohort reaches only `n_eff ≈ 49` under a 30-day half-life, so a `/50` target would leave narrow real cohorts perpetually provisional.)
- **Seller trust:** Beta-Binomial shrinkage with prior **μ₀ = 0.95, κ = 20**, plus a **Wilson lower bound at z = 1.2816**: `s_seller = 0.6·p_post + 0.4·LB`. No ratings ⇒ the S2-12 policy prior as an **explicit missing-data state** (flagged in the payload, never silently averaged in).
- **Fitness:** `s_fit = 0.5·T + 0.3·W + 0.2·C`.
  - `T` (suitability) from `DriveSpec.recording_tech`, `market_tier`, `media_type`, and — per **OQ16** — `dwpd` for SSDs: the endurance class folds into `T`, and the cohort key stays ADR 0011's four-part key.
  - `W` (verified warranty) from `ProductVariant.warranty_channel` + `warranty_months`. **Stubbed at the unverified tier for all of MS-2**, with a `warranty_unverified` provisional marker: `verification_event` exists as a table, but C.4 states that the manufacturer warranty-status lookup that would populate it "is **not yet scheduled in §7/§19**; the unverified-tier rubric fallback applies until it is." MS-2 does not schedule it.
  - `C` (condition) from `ProductVariant.condition` + `recert_channel`.
- **Availability:** a bounded rubric over the four `StockStatus` values that actually exist (`in_stock` / `out_of_stock` / `preorder` / `unknown`). ADR 0011 fixes only the endpoints — **in-stock 1.0, out-of-stock 0.0**; the `preorder` and `unknown` interior values are constants under S2-6 (versioned code, bumped and rescored when changed), not settings rows.
- **Vetoes**, per S2-8: `recording_tech = smr_dm` → cap 35; `condition ∈ {used, refurbished}` or `recert_channel = seller`, **and** `returns_policy = no_returns` → cap 60; `s_seller < 0.50` (strict) → cap 60.
- **Composition:** `base = Π_k max(s_k, 0.02)^{w_k}` at `price 0.50 · fitness 0.25 · seller 0.15 · availability 0.10`; `cap` = the minimum over triggered vetoes; `deal_score = round(100 · min(base, cap))`.
- **Accepted v1 calibration notes carried forward from ADR 0011, not "fixed":** the middle band is mildly generous (a median-priced backordered listing scored 69), the `0.02` subscore floor flattens the expensive tail (a top-decile-priced listing scored 14), and the seller-trust prior is sticky-high by design so the `< 0.50` veto fires only on substantial negative evidence. MS-2 reproduces the ratified model; re-fitting constants against real observations is explicitly out of scope.

### MS-2c — Cohort statistics and relaxation

- **Cohort key** = **capacity · tier · interface/form-factor · condition** (ADR 0011; four-part for SSDs too, OQ16). Derived from `DriveSpec.capacity_tb` (bucketed to nominal marketed capacity — exact decimal equality would shatter cohorts), `DriveSpec.market_tier`, canonicalized `DriveSpec.interface` + `form_factor`, and `ProductVariant.condition`. Stored as a deterministic string on both `cohort_baseline` and every `listing_score` row, so a historical score names the exact cohort it was scored in (NFR-007).
- **Input precedence when a listing is below model grain** (the ≥ 80% coverage reality, S2-10): authoritative `drive_spec` fields at model grain or better → the N2-extracted attributes already persisted in `offer_snapshot.attrs_json` (`capacity_bytes`, `condition`, `interface`, `form_factor`, written verbatim by `acquisition/persist.py`), tagged at a lower provenance in the payload → S2-7's neutral price subscore when even capacity is unavailable. A listing never fails to score because the matcher has not reached it.
- **Relaxation ladder**, fired when a cohort is too small: **relax condition → adjacent capacity → parent tier**, in that order, stopping at the first step that yields `n_eff ≥ 30`. The step that fired is recorded on `cohort_baseline` and in the explanation payload — a relaxed cohort must be visibly relaxed, not silently substituted.
- **Dirty detection** per S2-4; the 90-day pull per S2-5.

### MS-2d — Scoring service and the scheduled job

- `ScoringService.refresh()` — the two-phase run of S2-3, wrapped in a `ScraperRun(run_kind=score)` row with counts, runtime, and `RunFailureClass` on error, so NFR-004 covers scoring the same way it covers acquisition.
- **Write-on-change:** a new `listing_score` row is appended only when `deal_score`, the cap set, `is_provisional`, or `algorithm_version` changes. This is the same anti-spam rule `matching/resolver.py` already applies to `listing_resolution` edges ("no per-poll edge spam"), and it is what keeps a 60 s refresh interval from turning the hypertable into a write amplifier.
- **Idempotence contract:** scoring is a pure function of `(stored inputs, algorithm_version)`. Two consecutive refreshes over unchanged data write zero rows and leave `listing.current_deal_score` untouched. This is the acceptance test, not a comment.
- **Rescore triggers:** a dirty cohort; a listing whose `resolution_grain` changed (C.3.3: "a grain upgrade re-scores the listing"); an `algorithm_version` bump (full rescore).
- **Failure isolation:** a cohort that fails to score is logged, flagged, and skipped — it never aborts the refresh for other cohorts, mirroring NFR-001's per-source isolation.

### MS-2e — Real inputs, the glass box, and coverage

- eBay adapter extension: capture `seller.feedbackPercentage` and `feedbackScore` from the Browse `item_summary` payload into `SellerRatingObservation` (today `acquisition/sources/ebay.py` extracts only the username). Cassette-backed, PII-scrubbed per DR-006.
- Per-source `returns_policy` population and `seller_policy_prior` seeding (S2-12).
- **DR-004 completeness test:** every `listing_score` row carries input facts used, `algorithm_version`, thresholds and margins, confidence (`n_eff` / `λ` + the provisional marker), risk flags, the machine-readable payload, and the user-facing text. FR-006's percentile **+ margin-in-IQR**, seller evidence, fitness rubric pieces, and any cap reason are all present — MS-3 renders this payload; it does not compute anything.
- **Coverage report:** per-source model-grain-or-better percentage against C.3.5's **≥ 80% expectation**. A shortfall is reported and routed to the catalog/matcher backfill queue (`unknown_model_backfill`), never treated as an MS-2 blocker and never a reason to loosen ADR 0019's precision contract.

**MS-2 exit = spec §19 MS-2 acceptance (line 916):** every listing has a 0–100 score reproducible from stored inputs with a per-factor breakdown; thin-cohort listings (`n_eff < 30`) visibly shrink toward neutral and are marked provisional; the documented cohort-relaxation fallback fires on small cohorts; the ≥ 80% model-grain coverage figure is measured and reported as an expectation.

## 4. Error handling & ops (MS-2 posture)

- The `score-refresh` job writes a `ScraperRun(run_kind=score)` row per run — status, listings scored, cohorts refreshed, runtime, failure class (NFR-004). Scoring becomes visible in the same place acquisition already is.
- A per-cohort failure is isolated (MS-2d); a total refresh failure surfaces as a failed `ScraperRun` and, from MS-4, an operator alert. **No email alerts until MS-4** (ADR 0013) — the MS-1 posture is unchanged: DB rows, structured logs, and the §18.5 dead-man's switch.
- `max_instances=1` + `coalesce=True` are already the poller's `job_defaults`; scoring inherits them, so a slow refresh degrades to lower frequency rather than to concurrent double-writes. §14's "single user; `max_instances=1` per job; no locking/queueing design needed" holds for scoring too.
- **Capacity watch:** `listing_score` is a new write path onto the same disk as `offer_snapshot` and the raw payloads. Write-on-change (MS-2d) is the bound; the MS-1d disk-space alert (CT-116) covers the growth, and the TimescaleDB-aware dump pipeline must be confirmed to include the new tables before the first production refresh — the same pre-real-data check MS-1d ran, re-verified rather than assumed.
- An `algorithm_version` bump triggers a full rescore; at v1 scale that is a single long refresh, not a migration, and it is announced in the sub-milestone PR that bumps it.

## 5. Testing strategy

- **Unit (no DB) — the bulk of MS-2:** the entire `scoring/` pure library. Table-driven fixtures reproduce the ADR-0011 mock-data archetypes and their published bands; each of the three caps has a fires/does-not-fire pair; `n_eff` and `λ` carry property tests (monotonicity in observation count; `λ = 1` exactly at `n_eff = 30`); the seller prior has an explicit **0.50 boundary** test (S2-12); the geometric mean has a floor test proving `max(s_k, 0.02)` prevents a zero subscore from annihilating the product.
- **DB (live TimescaleDB):** the `listing_score` hypertable DDL and retention constraints (including the eBay-classed row that **must** carry `expires_at`); the 90-day windowed pull; relaxation over seeded thin cohorts; write-on-change idempotence; the grain-upgrade rescore path.
- **Reproducibility (NFR-007):** a golden test that re-derives a stored historical score from its own `inputs_json` + `algorithm_version` and asserts equality. This is the single test that proves DR-004 and NFR-007 together, and it is the one that fails if any score-shaping constant escapes into a mutable row (S2-6).
- **Explanation payload:** snapshot-tested (syrupy) so an accidental payload-shape change is a visible diff, since MS-3 renders it.
- Gate (`uv run python -m scripts.check`) green at every commit; each sub-milestone PR runs CI + dependency review.
